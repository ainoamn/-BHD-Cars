## المكدس الفعلي ونتائج الأوامر

المشروع يستخدم Next.js App Router وReact وTypeScript وTailwind CSS، ومنشور على Vercel. النسخ المثبتة أثناء الفحص: Next.js **15.5.29**، React وReact DOM **19.3.1**، TypeScript **5.9.3**، ESLint **9.39.5**. هذه تختلف عن الحد الأدنى الظاهر في `package.json` بسبب نطاقات `^`؛ يعتمد التكرار على lockfile و`npm ci`.

- `npx tsc --noEmit`: نجح.
- `npm run build`: نجح، وولّد الصفحات؛ السوق أظهر 159 kB ضمن First Load JS في تقرير البناء المحلي. هذا ليس قياس تحميل على جهاز مستخدم.
- `npm run lint`: لم ينجح كفحص آلي؛ دخل شاشة تهيئة ESLint تفاعلية وانتهى برمز1. لا يوجد إعداد ESLint مكتمل في الجذر، والأمر `next lint` معلن كمتقادم.
- `npm audit --omit=dev --json`: خروج1؛ مدخلان في شجرة الاعتماديات: Next بدرجة moderate وPostCSS المتداخل بدرجة high. العدّ هو عدد حزم متأثرة وفق npm، وليس عدد ثغرات قابلة للاستغلال عن بُعد ثبتت في BHD. لا يُستنتج منه اختراق الموقع. معالجة المسار والتوافق وإعادة الفحص مطلوبة قبل الإطلاق.
- لا توجد scripts لاختبارات وحدات أو تكامل أو E2E أو CI في الملفات الحالية.

مرجع إعداد ESLint: [توثيق Next.js](https://nextjs.org/docs/app/api-reference/config/eslint). مثال من التنبيهات التي أعادها npm: [PostCSS advisory](https://github.com/advisories/GHSA-fxqj-rqcc-2cmp). لا تُنفّذ `npm audit fix --force`؛ يلزم تحديث متوافق مع مراجعة تغييرات الإصدار واختبارات الانحدار.

## العيوب والفجوات مرتبة بالأولوية

### F01 — P0 — الطلبات ليست مشتركة ولا تصل إلى جهة تشغيل

التصحيح: API مصادق، قاعدة بيانات، request ID خادمي فريد، أحداث تسليم منفصلة عن إنشاء الطلب، ولوحة موظف وشريك. لا تظهر رسالة الاستلام من الشريك قبل تسجيل إقرار حقيقي.

القبول: ينشئ المستخدم طلبًا، يراه من جهاز آخر، تراه الجهة المسند لها وحدها، ويرى أثر التسليم والفشل وإعادة المحاولة.

### F13 — P2 — أصول الكتالوج وجودة العرض تحتاج ضبطًا

الدليل: `model-thumb.tsx` يحاول امتدادين ثم fallback؛ يتجاهل `src` عمدًا ولا يستخدم الصور الخارجية. توجد fallback باسم X-Trail عند غياب Xterra؛ `brand-logo.tsx` يجرب أربعة امتدادات. `Photo` يجعل كل الصور lazy، بما فيها صورة مقدمة الرئيسية.

التصحيح: manifest واحد لمسارات موجودة ونسبة أبعاد ونوع رسم، منع استبدال طراز بطراز مختلف، وسم رسم الكتالوج، فصل رسوم الفلتر عن صور السيارة الحقيقية، تحديد حقوق الأصول، وتحميل صورة LCP بالأولوية بعد قياس. الصور والشعارات لا تعتبر مراجعة بصرية مكتملة هنا.

القبول: طلب واحد لمسار موجود لكل أصل مع fallback هيكل مسمى بوضوح؛ لا يظهر X-Trail كـXterra؛ صور إعلان السيارة تخص السيارة المعروضة.

## مراجعة صفحات BHD صفحة صفحة

المقصود بالحالة أدناه الوظيفة من المصدر؛ جميع مسارات القائمة الحالية وصلت بـ200 في عينة HTTP.

1. `/`: مقدمة وبحث وفئات وسيارات ومزاد من بيانات ثابتة. المطلوب بحث مباشر بالسوق المختار، أقسام حسب توفر الخدمة، أعداد حقيقية، وإزالة «خدمات مكتملة/مباشر الآن» عند عدم التشغيل.
2. `/cars`: واجهة متعددة الفلاتر تعمل على8 سيارات محلية. المطلوب بحث خادمي وترقيم وصفحات URL وحقول مواصفات حقيقية ونطاق سوق وترتيب صحيح.
3. `/cars/[slug]`: صور ومواصفات ومقارنة وخدمات ورسالة محلية. المطلوب 404 وSEO، حالة بيع، هوية بائع موثقة، رسالة فعلية، تبليغ، مشاركة وصور وتقارير مصرح بها.
4. `/compare`: ثلاث سيارات من localStorage. المطلوب تفسير المفقود بدل التخمين، دعم إعلانات انتهت، حفظ للحساب ورابط مشاركة لا يكشف بيانات خاصة.
5. `/sell`: مدخل جاهز/حادث، مع لغة تذكر المنافس ورابط «أعلن لوحة» يذهب للتصفح. المطلوب اختيار بيع واضح يشمل اللوحة عبر نموذج إضافة مستقل.
6. `/sell/ready`: معالج متعدد الخطوات جيد كواجهة؛ المطلوب draft خادمي ورفع وحفظ VIN والمواصفات والمدينة والأصل والملكية وإقرار ثم مراجعة ونشر.
7. `/sell/accident`: خريطة ضرر وشحن وصور ودرجة إفصاح؛ المطلوب حفظ كل البيانات والملفات وفصل بلد المنشأ عن حالة الضرر عن موقع السيارة، وتقرير واضح للغرق/الحريق/الوسائد.
8. `/dealers`: دليل ثابت وشارات توثيق عامة؛ المطلوب اعتماد مؤسسات وفروع وبحث ومعلومات اتصال مؤكدة.
9. `/dealers/[slug]`: قائمة سيارات ثابتة؛ المطلوب ملف عام ومخزون منشور وتقييمات معاملات موثقة و404 وإجازة نشر بيانات المؤسسة.
10. `/valuation`: اختيار مثمن أو تلقائي؛ المطلوب matching فعلي وإسناد ومهلة قبول وتقرير معتمد ونسخ وإلغاء. سيارة خارج السوق تحتاج حقولًا فعلية أو سيارة محفوظة.
11. `/finance`: مقارنة محلية بثلاث خطوات؛ المطلوب بيانات أهلية وموافقات مستندات وعروض مزود وحالة قرار وصرف مستقلة، ومنع الإرسال بلا عرض.
12. `/insurance`: مقارنة محلية؛ المطلوب إدخال المؤمن له والسائق والاستخدام والملكية والمستندات ومقارنة تغطيات ودفع/إصدار وتجديد/مطالبة وإلغاء. ترتيب الدفع والإصدار يحدده عقد المزود؛ لا يعد النص الحالي وعدًا صالحًا لكل شركة.
13. `/inspection`: مركز وباقة ووقت رمزي؛ المطلوب تقويم فعلي وموافقة البائع وموقع وتفويض بالنيابة وفاحص وتقرير صور ونسخة نهائية قابلة للتحقق.
14. `/auctions`: لوتات ثابتة وعدّادات نسبية؛ المطلوب جلسات حالات وتسجيل مزايد وتأمين وسياسات مزاد وساعة خادم.
15. `/auctions/[slug]`: سجل ثابت ومزايدة محلية؛ المطلوب تنفيذ ذري وتحديثات فورية وإغلاق وترسية وفاتورة وتسليم ونزاعات وتأمينات.
16. `/import`: طلب نصي وتبويب حوادث؛ المطلوب عروض sourcing وتكلفة مفصلة وموافقة شراء وشحن ووثائق وتتبع وحالات فشل وتغير تكلفة؛ لا شراء خارجي تلقائي.
17. `/rental`: بطاقات وزر يسجل طلبًا؛ المطلوب صفحة سيارة وتواريخ وتوفر وأسعار نهائية وحجز ومنع تداخل وعقد وتأمين ضمان وتسليم/استلام.
18. `/parts`: قائمة وطلب بالـVIN؛ المطلوب تفاصيل قطعة ورقم OEM وتوافق ومخزون وعروض مورد وشحن وإرجاع وضمان.
19. `/scrap`: ساحات وأسعار طن ثابتة؛ المطلوب طلب سيارة وصور وملكية وتقدير مبدئي ووزن نهائي وإثبات استلام/إسقاط بحسب الإجراء المعتمد بالسوق.
20. `/plates`: بطاقات وطلب نقل؛ المطلوب إضافة لوحة والتحقق من الملكية وتفاصيل نوعها وسوقها ومراحل متابعة نقل؛ لا يدّعي النظام إتمام إجراء حكومي دون تكامل.
21. `/reports`: VIN وطلب محلي؛ المطلوب مزود تقرير وتوفر وحدود تغطية ودفع إن لزم وملف ووقت مصدره وسياسة استرداد عند عدم توفره.
22. `/service`: ورشة وملاحظة؛ المطلوب مركبة ومواعيد وخدمات وعرض عمل وموافقة قبل الزيادة وفاتورة وسجل صيانة.
23. `/requests`: سجل محلي بثلاث حالات؛ المطلوب نقله إلى `/account/requests` مع تفاصيل ومهام ناقصة وعروض ورسائل ومستندات وخط زمني وإلغاء وشكوى، وتحويل المسار القديم بعد تسجيل الدخول.
24. `/about`: وصف المشروع التجريبي ومقارنات منافسين؛ المطلوب تعريف BHD وقيمته وأدواره وحدود الخدمة وحقائق شركة مؤكدة.
25. `/contact`: بيانات تجريبية ونموذج محلي؛ المطلوب تذاكر دعم حقيقية وقناة رد ومكافحة إزعاج وبيانات اتصال معتمدة.

## اتجاه المنتج المقترح

القيمة الأساسية المقترحة: **ملف سيارة واحد ومعاملة قابلة للتتبع تربط المشتري والبائع والشريك والإدارة**. يبدأ التشغيل في عمان افتراضًا لأن البيانات الحالية متمحورة حولها، مع دعم بنية الأسواق والعملات من البداية. تُفعّل الدولة والخدمة بعد جاهزية الشريك والتشغيل؛ وجود اختيار دولة لا يعني جاهزية الخدمة فيها.

المرحلة التجارية الأولى: سوق سيارات فعلي + حساب مستخدم + لوحة إدارة + حساب معرض + طلب تثمين وفحص يعمل مع شركاء عبر بوابة. يلي ذلك التأمين والتمويل بعقود وواجهات محددة، ثم المزادات ذات الأموال والحجز والتجارة والاستيراد. يمكن تطوير الوحدات اللاحقة في staging أثناء تجهيز عقودها؛ لا تختزلها إلى نماذج تؤكد تسليمًا وهميًا.

مقاييس التفوق المستهدفة وليست نتائج حالية: نجاح إرسال الطلب90%+ في اختبار استخدام مضبوط، إمكان إكمال إعلان أساسي خلال5 دقائق في دراسة مستخدمين، زمن أول رد من الشريك حسب SLA تعاقدي، تسليم الطلبات المكتملة99%+ ضمن SLA، وCore Web Vitals عند p75: LCP≤2.5s وINP≤200ms وCLS≤0.1. تثبّت عينة القياس والسوق والأجهزة قبل مقارنة BHD بمنافس.

النص التفصيلي الملزم للتنفيذ ومعايير التحقق يأتي في الملفين التاليين.

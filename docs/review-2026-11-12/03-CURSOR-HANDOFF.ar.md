انسخ المقطع التالي إلى كورسر داخل مشروع `C:\dev\bhd cars`. يوجّه التنفيذ إلى الملفات المحلية بدل الاعتماد على ملخص المحادثة. التنفيذ يكون على دفعات؛ المراجعة الفنية اللاحقة تحتاج تسليم commit/diff والنتائج، ولا تنشأ تلقائيًا لمجرد مشاركة هذه التعليمات.

ابدأ بالدفعة BHD-001 فقط، ثم سلّم نتيجتها وفق القالب أدناه. بعد تسليم/مراجعة الدفعة تقدم للدفعة التالية بالترتيب المعتمد، ولا تتجاوز اعتمادياتها. لا تجمع كل المشروع في تعديل واحد، ولا توقف العمل لتطلب اختيارات روتينية سبق أن حسمتها المواصفات.

قبل أي تغيير:
1. اقرأ الحالة الفعلية الآن؛ هذه المراجعة تخص12 نوفمبر2026 وقد يكون الكود تغير بعدها.
2. وثق git status وHEAD والملفات التي ستلمسها. توجد تغييرات سابقة كثيرة للمستخدم؛ لا تحذفها أو تستبدلها ولا تستخدم git reset/clean لاستعادة نسخة قديمة.

قواعد التنفيذ الملزمة:
- لا تعتبر نجاح build دليلًا على اكتمال المنصة؛ نفذ دورة المستخدم والإدارة والشريك المطلوبة واختبارات المجال.
- localStorage مخصص لتفضيلات ضيف ومقارنة مؤقتة، وليس مصدر حقيقة للحسابات والطلبات والإعلانات والمزايدات أو الأموال.
- لا تؤكد إرسال طلب أو استلام شريك أو إصدار وثيقة أو حجز مورد إلا بعد نجاح العملية الخادمية المقابلة لها.
- كل API وServer Action وjob وتنزيل ملف يتحقق من الجلسة والصلاحية والملكية والمؤسسة والفرع والسوق والتكليف وحالة المعاملة.
- افصل التقدير المحلي عن عرض شريك صادر وعن وثيقة/قرار/تقرير معتمد؛ لا تصف seed أو اسمًا في data.ts بأنه شريك متعاقد.
- لا تكتب مصادقة أو تشفيرًا أو معالج دفع خاصًا من الصفر. طبّق المكتبات/المزودين المعتمدين بعد قراءة وثائق النسخ المثبتة.
- المبالغ بوحدات صغرى صحيحة مع عملة أصلية؛ العقود والعروض المقبولة لها snapshots؛ لا تأخذ السعر أو الدور أو الاعتماد من body باعتباره صحيحًا.
- المزايدة وقبول العروض وحجز التأجير والمخزون والدفع تحتاج منع تكرار وتزامنًا مضبوطًا في قاعدة البيانات.
- المستندات خاصة وروابطها قصيرة الصلاحية؛ quarantine وvalidation وscan قبل استخدامها؛ لا أسرار أو مستندات عملاء في public أو logs أو client bundle.
- لا تفعّل خدمة مالية أو عقد شريك أو تكتب إلى بيانات إنتاج لمجرد أن نموذجها اكتمل. جهّز الكود وstaging والاختبارات أولًا، وسجّل الاعتماد الخارجي الناقص بدقة. لا تختلق API أو ترخيصًا أو عقدًا أو بيانات شركة اتصال.
- لا تنشر للإنتاج أثناء دفعة تنفيذ إلا بتفويض نشر صريح قائم. افحص إعداد النشر التلقائي قبل push إلى فرع قد يشغل الإنتاج؛ لا تدفع إلى main كطريقة اختبار.
- إذا احتجت مدخلًا خارجيًا حقيقيًا، اطلبه محددًا وواصل الأجزاء المستقلة. اجعل الخدمة disabled أو assisted الحقيقي حسب الحالة؛ لا تستخدم mock وتعلن التكامل مكتملًا.
- كل مرحلة تشمل حالات الانتظار/الفشل/الإلغاء/التعافي، ونصوصًا عربية وإنجليزية قابلة للاستخدام على الهاتف.
- لا تعدل ملفات baseline في docs/review-2026-11-12؛ أدلة المراحل الجديدة تحفظ باسم مختلف مع commit SHA وتاريخ.

تسليم كل دفعة:
استخدم قالب التسليم الموجود في03-CURSOR-HANDOFF.ar.md، وأرفق diff/commit SHA وحالة git وأسماء الملفات وأوامر الاختبار والنتائج الفعلية ولقطات staging عند وجود واجهة وطلبات HTTP منقحة لإثبات الصلاحيات. حدد PASS/FAIL/BLOCKED لكل معيار قبول.

## قالب تسليم كل دفعة

ينشئ المنفذ ملفًا واحدًا مثل `docs/implementation/BHD-001.md` بالمحتوى التالي، دون أسرار أو بيانات شخصية:

```markdown
# BHD-001 — اسم الدفعة

التاريخ:
الفرع:
HEAD قبل العمل:
commit التسليم أو مرجع diff:
نطاق التعديلات السابقة التي تداخل معها العمل:

## المشكلة والسلوك الناتج

وصف موجز مع مثال قبل/بعد.

## الملفات والتغييرات

المسارات الفعلية وسبب كل مجموعة تغييرات.

## معايير القبول

- المعيار الأول: PASS/FAIL/BLOCKED — الدليل أو رابط مخرجاته.
- بقية المعايير من backlog دون حذف غير المار منها.

## التحقق المنفذ

- نسخة Node والحزم المؤثرة.
- الأمر الدقيق ونتيجته ورمز الخروج، مع تمييز الاختبارات المنفذة عن المخطط لها.
- بيئة الاختبار ومصدر بياناتها وهل استخدم mock/sandbox/مزودًا حقيقيًا.
- E2E والأطراف المستخدمة ونتائج API السلبية بعد تنقيح الأسرار.
- المقاسات واللغات واللقطات عند تعديل واجهة.

## البيانات والصلاحيات والتشغيل

الترحيلات والقيود، التفويض، أثر cache، المهام والإشعارات، متغيرات البيئة بأسمائها فقط.

## المخاطر والاعتماديات المتبقية

ما لم ينفذ ولماذا وأثره على الإطلاق؛ المدخل الخارجي المطلوب إن وجد.

## التراجع

طريقة تعطيل الميزة/العودة الآمنة مع الحفاظ على البيانات، وما لا يمكن عكسه تلقائيًا.

## حالة git النهائية

ملخص الملفات المعدلة والجديدة والمتروكة من عمل سابق، دون إخفاء فرق غير ملتزم.
```

لا يلزم حفظ مخرجات اختبارات تحتوي أسرارًا أو بيانات مستخدمين كاملة. يسجل المنفذ transcript منقحًا ويفضل روابط CI أو ملفات نتائج آلية مع provenance. لا يغني screenshot عن قيد قاعدة بيانات أو تحقق صلاحية.

## بروتوكول المراجعة التقنية بعد تسليم كورسر

يرسل المستخدم رقم الدفعة وcommit/diff أو يطلب مراجعة التعديلات الموجودة في نفس مساحة العمل. عندها يراجع المدقق الحالة الحقيقية؛ لا يكتفي بتقرير «تم» من المنفذ.

1. تثبيت النطاق: قراءة AGENTS والتعليمات والدفعة وgit diff، ومقارنة التعديلات بالـbaseline والتغييرات السابقة.
2. تتبع رحلة البيانات: UI → API/Action → policy/schema → domain service → transaction → DB/file → outbox/worker → provider → webhook → UI.
3. فحص المشاكل المؤثرة: IDOR وعزل المؤسسات وتغيير الأدوار والملكية والحقول الزائدة وcache والتزامن والتكرار والتسريب والعمليات المالية وحالات الفشل.
4. تشغيل الأوامر المناسبة للدفعة في بيئة آمنة. قراءة الاختبارات وتحدي افتراضاتها، لا مجرد إعادة تشغيل اختبار يطابق التنفيذ.
5. التحقق من رحلة أحد الأطراف الثلاثة مع البقية: لا قبول لواجهة مستخدم ترسل طلبًا لا يمكن لموظف حقيقي التعامل معه.
6. إصدار ملاحظات P0/P1/P2 مع مسار وسطر حالي وسبب وطريقة إعادة إنتاج وأثر ومطلوب قبول. قد تختلف أسطر المصدر بعد التطوير؛ لا يعاد استخدام أرقام مراجعة قديمة بلا فحص.
7. فصل العيوب المؤكدة عن مخاطر غير محسومة والاعتمادات الخارجية. عدم وجود ملاحظات لا يعني اختبار اختراق شاملًا أو موافقة قانونية.
8. كورسر يصلح الملاحظات في نفس النطاق، يعيد الاختبارات المتأثرة ويقدم diff جديدًا؛ تراجع الإصلاحات قبل إعلان مرور البوابة.

### أمثلة سيناريوهات يجب أن يتحدى بها المراجع التنفيذ

- العميل يغيّر `requestId/organizationId/fileId` في HTTP إلى سجل مؤسسة أخرى.
- موظف دعوة يحاول منح صلاحية لا يملكها، أو استعمال دعوة بعد استهلاكها، أو بقاء دور بعد تعليق العضوية.
- العميل يقبل عرضين متزامنين أو عرضًا تغيرت شروطه أو انتهت صلاحيته.
- مزود يدفع callback نجاح مرتين أو بعد callback متأخر أقدم، والworker يعاد تشغيله بين DB وإرسال الرسالة.
- قبول مزايدة مع بلوغ وقت النهاية أثناء القفل، وتداخل job إغلاق مع bid، وتبديل ساعة الجهاز.
- حجزان لنفس السيارة، أو شراء آخر قطعة، أو charge/refund متكرر بمفاتيح مختلفة بعد timeout غير محسوم.
- ملف هويّة يحاول الظهور في public CDN أو في export أو related entity، ورابط تنزيل بعد سحب التفويض.
- تغيير اسم طراز أو سعر صرف أو قواعد ضريبة اليوم يغير عرضًا/عقدًا/فاتورة صدرت أمس.
- إسناد مثمن انتهى اعتماده أو فقد فرعه أو رفض البائع دخول الفاحص.
- API مزود غير متاح، ولا مرشح متاح، ورفع صورة يتوقف منتصفه، وعودة المستخدم للمسودة من جهاز آخر.

## مدخلات التشغيل التي يحتاجها الإطلاق الفعلي

لا تمنع هذه المدخلات تنفيذ جودة الكود والبيانات والواجهات الآمنة في staging، لكنها تمنع ادعاء تشغيل الخدمة المعنية قبل الحصول عليها:

- الاسم القانوني وبيانات الاتصال والنطاق والأسواق الأولى ومالك التشغيل الفعلي.
- أسماء شركاء متعاقدين ودليل اعتماد نشاطهم وأسواقهم وفروعهم وSLA ومن يمثلهم في UAT.
- عقود وعينات مستندات ومسار عمل ومفاتيح sandbox/وثائق API لكل تأمين/تمويل/تقرير/رسائل/دفع؛ تبقى الأسرار في secret manager فقط.
- قواعد الرسوم والعمولات والضرائب والإلغاء والاسترداد والتأمينات والتسوية والمستفيدين وموافقاتها بحسب السوق والنشاط.
- سياسة خصوصية واحتفاظ وموافقة مشاركة وشروط أصلية معتمدة، وآلية دعم وشكاوى وتفويض فحص بالنيابة.
- حسابات خدمات DB/storage/worker/observability ونطاقات إرسال SMS/بريد وإعداد DNS بعد تفويضها، واختبار استعادة.
- اختيار PSP يدعم السوق والعملات ونشاط الجهة والضمان/الاستردادات المطلوبة، لا مجرد زر دفع عام.

## ما يُطلب من كورسر أولًا وما يؤجل

ابدأ بـBHD-001. لا تبدأ بإعادة رسم الشعارات أو زيادة بنرات الخدمات أو تصميم عشرات لوحات فارغة. بعد تثبيت الجودة والنسخ، نفّذ أساس البيانات والحساب والمؤسسات والملفات، ثم سلّم أول مسار كامل: **إعلان حقيقي → طلب تثمين → شريك معتمد → تقرير → متابعة مستخدم وإدارة**. بعدها توسّع في الخدمات وفق اعتمادياتها؛ ليس مطلوبًا تشغيل كل سوق وكل خدمة في أول إطلاق.
